# AGENTS.md

## Назначение репозитория

Это Control Plane Server — backend Admin Panel централизованной системы
управления ботами Polymarket. Сервер управляет множеством изолированных
экземпляров бота: их регистрацией, runtime-конфигурациями, командами
и активацией. Он принимает события и результаты выполнения от ботов.

В этом репозитории разрабатывается исключительно backend.
Frontend Admin Panel находится вне области работы: не проектируй
и не реализуй здесь страницы, компоненты интерфейса и клиентскую логику.
API для взаимодействия с frontend входит в ответственность backend.

Control Plane Server — источник истины для управляющего состояния системы.
Боты — stateful execution plane, исполняющий полученные инструкции.

Один запущенный экземпляр бота работает только с одним аккаунтом Polymarket.
На одном сервере (и IP) работает только один экземпляр бота. Для нескольких
аккаунтов используются отдельные изолированные серверы/экземпляры.

Control Plane Server определяет, **что** и с какими параметрами требуется
сделать; бот определяет, **как** выполнить это в рамках торговой и доменной
логики. Исполнение стратегий и работа с торговыми API остаются на стороне бота.

## Модель состояния

Control Plane Server — stateless-процесс. Всё состояние приложения
хранится в БД и/или внешнем кеше. Не используй глобальные переменные,
объекты процесса или локальные файлы как хранилище состояния приложения.

В памяти процесса допустимы временные данные текущей обработки,
клиенты БД и транспорта, соединения и другие технические ресурсы.
Корректность работы не должна зависеть от сохранения этих объектов
между запросами, сообщениями или перезапусками.

Разделяй управляющее состояние и наблюдаемое состояние ботов:

- управляющее состояние: зарегистрированные экземпляры, их привязки
  к аккаунтам, версии конфигураций, требуемая активация, выданные команды
  и полученные результаты;
- наблюдаемое состояние: сведения, полученные от ботов, включая применённую
  конфигурацию, фактическую активность, позиции, ордера и состояние стратегий.

БД — источник истины для долговременного управляющего состояния:
регистраций, привязок к аккаунтам, конфигураций, команд и результатов.
Кеш хранит временные данные с явно определёнными сроками жизни
и поведением при их отсутствии. Конкретные технологии определяются
архитектурой проекта.

Перезапуск или замена процесса backend не должны приводить к потере
управляющего состояния. Обработка запросов и сообщений не должна
требовать их попадания в тот же экземпляр backend.

Если нужны дедупликация, блокировки или координация обработчиков,
обеспечивай их через БД/внешний кеш. Локальная память процесса
не обеспечивает координацию между экземплярами backend.

Оперативное торговое состояние хранится в памяти процесса бота.
Полученные сервером сведения являются последним известным состоянием
и могут устаревать. Учитывай время их получения и принадлежность конкретному
запуску бота. Не меняй модель хранения состояния бота.

Не приравнивай требуемое состояние к фактическому. Сохранение конфигурации
не означает её применения, отправка команды — её выполнения, а потеря
связи — остановки торговли.

## Конфигурация и активация

Сервер должен поддерживать обязательную последовательность запуска бота:

```text
CLI bootstrap → инициализация transport → подключение к Control Plane
→ регистрация bot instance → получение runtime-конфигурации
→ валидация и инициализация → активация Admin Panel → торговая логика
```

Проверяй конфигурацию на стороне сервера до её отправки. Это не заменяет
валидацию и инициализацию на стороне бота.

Активация допускается после подтверждения ботом успешной валидации
и инициализации с соответствующей версией конфигурации.
Учитывай подтверждения в контексте конкретного запуска бота:
ответ от предыдущего запуска не подтверждает готовность текущего.

Регистрация и восстановление соединения сами по себе не являются
разрешением на торговлю. Не добавляй неявную активацию.

## Граница ответственности: сервер, frontend и боты

ИИ работает исключительно над backend Control Plane Server:
его прикладной логикой, БД, кешем, API и взаимодействием с ботами.

Frontend Admin Panel, боты и транспортная инфраструктура — отдельные
компоненты. Не реализуй и не изменяй их внутреннюю логику в этом репозитории.
Не предполагай, что изменение сервера автоматически изменяет их поведение.

Сервер отвечает за:

- проверку входных данных и прав на управляющие действия;
- регистрацию и идентификацию экземпляров бота;
- хранение и передачу runtime-конфигураций;
- адресную отправку команд и сигналов активации;
- приём и учёт подтверждений, событий и результатов;
- предоставление frontend состояния системы и результатов действий.

Не переноси на сервер исполнение стратегий, управление торговыми ордерами
через API Polymarket или восстановление внутренних объектов торговой
модели бота. Сервер передаёт инструкции и учитывает результаты исполнения.

Для разработки и тестирования допускаются заглушки транспорта и сообщения
ботов по согласованному контракту. Не требуй запущенного frontend или
реальной торговли для проверки прикладной логики сервера.

## Контракты и надёжность взаимодействия

Опирайся на явно описанные входные и выходные контракты. Если необходимое
поведение бота не подтверждено контрактом, обозначь пробел и согласуй
изменение; не считай это поведение уже реализованным.

Связывай команды, подтверждения и результаты по идентификаторам.
Различай отправку, принятие и завершение команды.
Таймаут ожидания результата не доказывает, что команда не выполнена.

Учитывай повторную доставку, задержки, нарушение порядка сообщений,
разрывы соединения и перезапуски. Повторная обработка сообщения не должна
создавать повторные управляющие действия. Повторную отправку команд
с побочными эффектами допускай только с учётом гарантий контракта.

Проверяй принадлежность сообщений экземпляру бота и аккаунту.
Изолируй адресацию, конфигурации и команды разных экземпляров.
Не записывай секреты и полные конфигурации с секретами в логи.

## Работа с пользователем и изменениями

Не выполняй команды в терминале и не изменяй существующие файлы без
предварительного явного разрешения пользователя. Сначала сообщи:

1. зачем требуется действие;
2. какие именно файлы или команды оно затрагивает;
3. полный предполагаемый diff изменений.

Когда ты пишешь diff то сначала указывай в каком файле изменения.

После этого дождись явного согласия. Не считай молчание согласием.

Не создавай и не удаляй файлы без отдельного согласия. Перед созданием объясни
зачем нужен файл, предложи конкретное имя и спроси, устраивает ли оно
пользователя. Удаление также требует назвать точные цели и дождаться
подтверждения. ИИ не выполняет самостоятельно никакие действия с Git
(включая чтение статуса и истории, создание и изменение веток, добавление,
удаление и откат изменений, commit, amend, push, pull, merge и rebase).
Если пользователь явно попросил выполнить конкретное действие с Git, его
разрешение считается полученным только для этого действия и его необходимого
непосредственного контекста. Если действие с Git не было явно запрошено
пользователем, но требуется ИИ, ИИ сначала объясняет, зачем оно нужно,
называет точную команду или набор команд и ждёт явного разрешения.

Чтение файлов и диагностика тоже требуют предварительного разрешения, потому
что для них используется терминал. Если пользователь уже явно разрешил
конкретное действие в текущем сообщении, повторно разрешение не запрашивай, но
не расширяй его область.

## Подход к решениям

Не принимай предложение пользователя автоматически. Сначала проверь его на
корректность, риски, совместимость с этой архитектурой и возможное ухудшение
кода. Если для задачи есть более подходящий паттерн или несколько разумных
вариантов, прямо объясни разницу и предложи лучший вариант до внесения
изменений.

Отвечай по существу, прямолинейно и кратко: без приветствий, извинений,
повторения вопроса, лести и формальной вежливости. Не скрывай риски и не
соглашайся с решением, которое ухудшает архитектуру.
